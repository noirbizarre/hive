# Roadmap

Hive's goal is to provide one shared session manager and a unified interface for
ACP coding agents. A session has a stable identity independent of the client
that created or currently controls it. **Only one client controls a session at
a time**, but control can move between the TUI, WebUI, ZJHive, and eventually
the agents' native interfaces.

The first release prioritizes sessions created through Hive. Attaching to
sessions created directly in OpenCode or Pi is a planned later capability, not
a prerequisite for the first release.

## Release management

The release PR [#11 — 0.1.0](https://github.com/noirbizarre/hive/pull/11) is
generated by **gh-ship**. It is a release artifact, not an implementation task
or a signal that the release scope is complete. Keep it open while implementation
continues; merge it only when the agreed 0.1.0 scope is complete and validated.
Do not merge it just to unblock other roadmap work, and do not hand-edit its
generated changelog/version content as a substitute for completing the scope.

The intended 0.1.0 scope is the initial Hive-owned session workflow: the shared
session/control contract (#3), real-agent ACP compatibility checks (#4), and
the unified TUI and WebUI handoff flow (#7 and #8), with CI and documentation
green. ZJHive attach/prompt support (#9) is in the current cross-client roadmap;
keep it in the 0.1.0 gate if it remains part of the release target, or explicitly
move it out of scope before calling the release ready. Native-session adoption
(#5 and #6), durable restart recovery (#10), expanded runtime activity (#17),
and token/cost accounting (#18) are follow-up capabilities, not automatic
blockers for the initial release.

When the scope is complete, review the gh-ship-generated PR and changelog,
verify CI and relevant smoke/compatibility tests, then merge the release PR.

## Current focus

### Phase 0 — Stabilize the bootstrap

- Finish fixing CI and keep `mise run ci` green.
- Preserve the `rust.tpl` / `git-tpl` workflow; inspect template-owned changes
  before editing generated files.

### Phase 1 — Establish session ownership and verify agents

These can proceed in parallel:

- [#3 — Shared session manager with exclusive, transferable control](https://github.com/noirbizarre/hive/issues/3)
  - Stable Hive session IDs; separate session, client, agent process/connection,
    and downstream ACP session lifetimes.
  - Atomic control handoff, stale-controller rejection, detach/reconnect, event
    cursors/replay, and no duplicate prompts or generations.
- [#4 — Real-agent ACP compatibility and lifecycle tests](https://github.com/noirbizarre/hive/issues/4)
  - Establish what installed Pi and OpenCode versions actually support.
  - Keep real-agent tests opt-in; normal CI remains deterministic.

**This is the foundational phase.** Define the session and handoff contract here
before implementing independent lifecycle logic in any client.

### Phase 2 — Deliver the unified TUI and cross-client handoff

Once the shared session contract is implemented, work on the clients:

- [#7 — Unified Hive TUI](https://github.com/noirbizarre/hive/issues/7) — primary
  interface; create, list, resume, and control sessions with consistent tool,
  permission, input, and cancellation handling.
- [#8 — WebUI session resume and control](https://github.com/noirbizarre/hive/issues/8)
  — open the same session ID, take control, send another prompt, and reconnect
  without forking the conversation.
- [#9 — ZJHive attach and prompt submission](https://github.com/noirbizarre/hive/issues/9)
  — select an existing session and take control from within Zellij. ZJHive must
  reuse the daemon's session manager and reconcile activity after missed updates.

The target workflow is: start in the TUI, continue in the WebUI, then resume or
submit another prompt from ZJHive. Every transition uses the same Hive session
and downstream agent session. The previous client loses mutation rights when
control is transferred. Confirm explicitly whether the ZJHive step is required
for 0.1.0 before merging the release PR.

### Phase 3 — Stream runtime activity

- [#17 — Stream live agent activity, tool calls, and todo updates](https://github.com/noirbizarre/hive/issues/17)

Normalize native agent activity, tool/task lifecycles, late/background updates,
and reconnect snapshots/replay. This builds on the shared event contract and
improves the clients' live view. Advanced tool/todo visibility is a follow-up
unless it is needed to satisfy an explicitly agreed 0.1.0 acceptance criterion.

### Phase 4 — Persist and recover Hive sessions

- [#10 — Persist session metadata and recover after daemon restart](https://github.com/noirbizarre/hive/issues/10)

Do this after the lifecycle, event cursor, and recovery capabilities are
understood. Persisting a session record does not necessarily mean an agent
process or active generation can be restored. Report recovery state honestly;
never silently create a replacement session or resend a prompt.

### Phase 5 — Track usage and estimate costs

- [#18 — Track model token usage and estimate per-call and session costs](https://github.com/noirbizarre/hive/issues/18)

Capture provider-reported usage, aggregate it without double-counting retries or
sub-agent calls, and estimate costs only when matching pricing data is available.
Keep actual provider-reported costs distinct from estimates.

### Phase 6 — Establish Pi ACP compatibility

- [#19 — Establish and document Pi ACP entrypoint compatibility](https://github.com/noirbizarre/hive/issues/19)

Determine the supported Pi entrypoint/adapter and tested versions, and document
the capability matrix. This is an investigation that can run in parallel with
Phases 3–5; it does not itself implement native-session adoption.

### Phase 7 — Adopt sessions created in native agent interfaces

These are separate, longer-term integrations and are not first-release blockers:

- [#5 — OpenCode server v2 persistent sessions](https://github.com/noirbizarre/hive/issues/5)
  — discover and attach to sessions created directly in OpenCode, and resume
  Hive-created sessions there where its server APIs allow it.
- [#6 — Pi persistent sessions](https://github.com/noirbizarre/hive/issues/6)
  — discover and attach to sessions created directly in Pi, and resume
  Hive-created sessions in Pi where its supported persistence APIs allow it.

Both depend on the shared session contract and real-agent capability testing.
For Pi, use the findings from #19. ACP compatibility alone does not guarantee
that an existing native session can be adopted. Do not silently create a
duplicate conversation when adoption is unsupported.

## Architectural invariants

- One Hive daemon per local user; clients never launch their own agent for an
  existing Hive session.
- A Hive session, client connection, downstream agent process/connection, and
  downstream session have distinct identities and lifetimes.
- At most one client can issue state-changing operations for a session at once.
- A handoff invalidates the old controller; stale commands are rejected.
- Detaching a client does not stop an active generation.
- Reconnect and replay must not duplicate messages, prompts, or generations.
- Keep the client-facing protocol ACPv2; use explicit adapters for agent-specific
  or native-server integration.
- Keep the current local-trusted-user security boundary explicit; do not imply
  remote multi-user authorization exists.
- Update tests and documentation with each issue. Preserve template-owned
  configuration and use the repository's documented `mise` tasks.

1. Keep CI green and preserve the template workflow.
2. Finish/verify #3 and #4 (already closed; keep their guarantees covered by tests).
3. Finish #7 and #8; finish #9 too if ZJHive remains in the agreed 0.1.0 scope.
4. Validate the 0.1.0 scope, review the gh-ship-generated PR #11, then merge it
   only when the release gate is satisfied.
5. Implement #17 for richer live runtime activity.
6. Implement #10 once session recovery and event history semantics are explicit.
7. Implement #18 usage/cost accounting; this can proceed in parallel once the
   call/session identity model is stable.
8. Investigate #19, then implement #5 and #6 as separate optional integrations
   after validating each agent's actual native session APIs.
